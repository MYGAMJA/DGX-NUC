## 단계 1 — System Identification (실로봇 측정)

> **한 줄 요약:** 시뮬레이션에서 가정한 로봇과 실제 만든 로봇이 얼마나 똑같은지 측정하는 작업.
>
> D4 정책은 "내가 19.89kg이고 모터가 즉시 반응한다"고 가정하며 학습됐음. 실제 로봇이 다르면 (예: 더 무겁거나 모터가 느리거나) 정책이 헷갈려 넘어질 수 있음. 그래서 **실제 로봇이 시뮬 가정과 얼마나 다른지** 5가지를 측정.
>
> **비유:** 종이 위 그림으로 자전거 연습한 사람이 진짜 자전거 타려면, 두 자전거의 무게/크기/핸들 반응이 같은지 먼저 재봐야 함. System ID는 **그 차이를 미리 측정해두는 작업**.

---

### 1-1. 무게 재기 (반나절)

#### 왜 하는지

시뮬은 "이 로봇 19.89kg, 다리 0.8kg, 팔 3.44kg" 가정. 진짜 만든 로봇이 21kg이면 다리 힘이 부족해서 넘어질 수 있음.

#### 뭘 하는지

**평범한 전자저울 (10g 정밀도)** 으로:

| # | 항목 | 방법 | 비교 대상 |
|---|------|------|----------|
| 1 | 전체 robot 무게 | 저울 위에 통째로 | URDF 가정 19.89 kg |
| 2 | base body 무게 | 다리 분리 후 base만 | URDF base mass 4.83 kg |
| 3 | 다리 1개 무게 | 분리 후 측정 | URDF leg chain (좌/우) |
| 4 | SO-ARM 양 팔 무게 | 분리 후 측정 (3.44 kg × 2 가정) | URDF SO-ARM lumped mass |
| 5 | 발 (foot) 무게 | 분리 가능 시 | URDF ankle_roll 부분 |

#### 결과 의미

- **차이 5% 이내** (20kg 기준 1kg 이내) → "비슷하네, 그냥 진행"
- **차이 5~15%** → URDF 파일에 실측치 적어두기
- **차이 15% 이상** → 시뮬 모델 수정 필수, 재학습 검토

**보정 대상 파일:** `sim/isaaclab/robot/hylion_v6.urdf`, `hylion_v6.xml` (MJCF)

---

### 1-2. 무게중심 (CoM) 찾기 (반나절)

#### 왜 하는지

같은 20kg이라도 무게중심 위치가 다르면 균형 잡는 법이 달라짐. **사람도 배낭을 앞에 메느냐 뒤에 메느냐에 따라 자세 바뀌는 것**과 같음.

시뮬은 "이 다리의 무게중심은 무릎에서 5cm 위" 식으로 가정. 실제로는 부품 배치 때문에 다를 수 있음.

#### 뭘 하는지

**"칼날 위 균형 잡기" 방법:**

1. 다리(또는 팔, base)를 분리해서 따로 둠
2. **얇은 자나 막대 위에 올림** → 자 위치 이리저리 옮겨가며 **안 떨어지는 지점** 찾기
3. 그 지점이 그 link의 무게중심 (한 방향)
4. 90도 회전해서 다시 → 또 다른 방향
5. 3D는 매달기 실험: 줄에 매달면 무게중심이 줄 바로 아래

| link | 측정 축 | 비교 대상 |
|------|--------|----------|
| base | x, y, z | URDF `<inertial origin xyz="...">` |
| upper leg (hip ~ knee) | x, z | URDF leg link |
| lower leg (knee ~ ankle) | x, z | URDF |
| foot | x, y, z | URDF |

#### 결과 의미

- **차이 1cm 이내** → OK
- **차이 1~3cm** → URDF 보정
- **차이 3cm 이상** → 정책이 균형 못 잡을 위험. 보정 필수

### 1-3. 모터 반응 속도/한계 측정 (1일)

#### 왜 하는지

시뮬에선 "모터에게 30도 회전해라" 명령 → **즉시 30도** 가는 걸로 가정.

실제 모터는:
- ⏱ **반응 지연** — 명령 받은 후 움직이기 시작까지 5~10ms 걸림 (학습은 0ms 가정)
- 🐢 **응답 속도** — 30도 도달까지 시간 걸림
- 💪 **힘 한계** — 6Nm까지 낼 수 있다 가정했는데 실제는 5Nm일 수도
- 🔩 **마찰** — 작은 명령에는 안 움직임 (정적 마찰)

#### 뭘 하는지

**한 관절씩 (예: 왼쪽 무릎) 테스트.** 데이터 로거로 encoder/torque 기록.

```python
# 의사 코드
for joint in ["leg_left_hip_pitch", "leg_left_knee_pitch", "leg_left_ankle_pitch"]:
    # 1) step torque command (0 → 3 Nm)
    log_start = time.now()
    set_torque(joint, 3.0)
    while time.now() - log_start < 0.5:
        log(time, encoder_pos, encoder_vel, torque_estimated)
    set_torque(joint, 0)

    # 2) step position command (0 → 0.5 rad)
    set_kp_kd(joint, 20, 2)
    set_target_pos(joint, 0.5)
    log_5sec()
```

**추출할 파라미터:**

| 파라미터 | 측정 방법 | 의미 | 비교 대상 |
|----------|----------|------|----------|
| **모터 반응 지연** | 명령 시각 ↔ encoder 움직이기 시작 시각 | 명령받고 멈칫하는 시간 | 학습 0ms 가정 |
| **time constant** | step 응답의 63% 도달 시간 | 천천히 도달하는 정도 | 학습 즉시 응답 |
| **kp/kd 검정** | step response curve fitting | PD 제어 게인 진짜 값 | 학습 kp=20, kd=2 |
| **max torque** | 점진 토크 증가 → saturation | 모터가 낼 수 있는 최대 힘 | 학습 6 Nm |
| **정적 마찰** | 매우 작은 토크 → 움직이기 시작 | 멈춰있을 때 저항 | 학습 0.1 frictionloss |
| **동적 마찰** | 일정 속도 회전 시 토크 | 움직일 때 저항 | viscous coefficient |

#### 결과 의미

- 모터 반응 지연 > 5ms → **학습 환경에 latency randomization 추가** 필요
- 실제 kp가 학습값과 30% 이상 다름 → `robot_cfg.py` 의 stiffness 보정
- max torque 실측 < 6 Nm → effort_limit 낮춰서 재학습 검토

### 1-4. 센서 노이즈 측정 (반나절)

#### 왜 하는지

로봇 IMU(자이로/가속도계)와 encoder는 완벽하지 않음. **정지 상태에서도 미세한 떨림(노이즈)** 있음.

시뮬은 "노이즈 ±0.3 rad/s" 정도라 가정하고 학습. 실제 센서 노이즈가:
- 더 작으면 → ✅ 학습이 더 어려운 환경 가정한 거라 안전
- 더 크면 → ⚠ 정책이 헷갈림 → 비틀거림 위험

#### 뭘 하는지

**가만히 두고 1분 데이터 수집:**

```bash
# 정지 자세로 1분 데이터 수집
ssh nuc 'python3 sim/mujoco/collect_imu_noise.py --duration 60 > imu_static.log'
# 분석
python3 analyze_imu_spectrum.py imu_static.log
```

```
1. 로봇 정지 자세로 세움 (전원만 켜고 모터 명령 X)
2. 60초 동안 IMU (각속도, 회전) 기록
3. 60초 동안 encoder (관절 각도) 기록
4. 데이터의 분산(흔들리는 정도) 계산
```

→ 정지 상태인데도 데이터가 흔들리는 정도 = 노이즈 크기

#### 결과 의미

학습 가정 vs 실제 비교:
- IMU 각속도 노이즈: 학습 ±0.3 rad/s
- 중력 방향 노이즈: 학습 ±0.05
- 관절 각도 노이즈: 학습 ±0.05 rad

**판정:**
- 실측 < 학습 → 충분히 강건 (학습이 보수적)
- 실측 > 학습 → 학습에 더 강한 noise randomize 후 재학습 권장

### 1-5. 통신/제어 속도 측정 (반나절)

#### 왜 하는지

로봇 보행은 **25Hz (1초에 25번)** 제어 루프로 동작. 즉:

```
40ms 안에:
  센서 읽기 → 정책 계산 → 모터 명령 보내기
```

이걸 못 맞추면 정책이 "지각"해서 보행이 휘청거림. 특히 NUC가 모터 통신 + 정책 추론 + Orin 통신 동시에 하니까 병목 가능성 있음.

#### 뭘 하는지

**1000번 측정:**

```python
for i in range(1000):
    t0 = time.now()
    obs = get_observation()      # 센서 읽기 (IMU + encoder)
    action = policy(obs)          # 신경망 forward pass
    set_action(action)            # 모터에 토크 보냄
    t1 = time.now()
    log(t1 - t0)                  # 한 사이클 걸린 시간
# 결과: 25Hz (40ms) 충족 여부 + 평균/최대 시간
```

#### 결과 의미

- **평균 < 40ms** → 25Hz 유지 OK
- **평균 > 40ms** → 어딘가 느림. CPU 사양 확인 / 코드 최적화 / 통신 방식 변경 필요

**Sim 환경 보정 + 재학습:**

1. 학습 환경에 추가 randomization:

# env_cfg.py 또는 env_cfg_BG.py에 추가

**위험:** 재학습 또 실패 가능성. 단계 3-A/B로 끝낼 수 있으면 그게 최선.

## 단계 4 — Sim2Real 점진 검증

가장 안전한 시나리오부터 점진 위험 증가. 매 단계 안전 확인 후 다음.

### Step 1 — 정지 자세 (가장 안전)

```bash
# 30초 정지 유지 검증
DISPLAY=:0 python3 nuc/bhl/run_policy.py \
  --ckpt stage_d4_hylion_v6/best.pt --vx 0 --duration 30
```

**기준:**
- ✅ 30초 직립 유지 → Step 2 진행
- ⚠ 5~30초 사이 fall → 정책 약함, 단계 3 보정 필요
- ❌ 5초 미만 fall → sim2real gap 매우 큼, 단계 3 필수

### Step 2 — 매우 느린 보행 (vx=0.1)

```bash
# 10초 보행
python3 nuc/bhl/run_policy.py --vx 0.1 --duration 10
```

**기준:**
- ✅ 10초 안정 보행 → Step 3
- ⚠ 휘청거림 → vx 더 낮춤 (0.05) 시도
- ❌ Fall → 단계 3 재보정

### Step 3 — 점진 속도 증가

```
vx=0.1 → 0.2 → 0.3 → 0.5
각 5~10초 안정 보행 확인 후 다음 속도
```

각 속도에서:
- Forward 보행
- 좌/우 미세 회전 (ang_vel ±0.3)
- 정지 transition (vx=0 명령으로 멈춤)

### Step 4 — 환경 변화

**4-1. payload 추가 (점진):**
```
0 kg → 0.5 kg → 1 kg → 2 kg
각 payload에서 정지 5초 + 보행 vx=0.3 5초
```

**4-2. 가벼운 push:**
- 손가락으로 base 가볍게 push (~5N)
- 회복 여부 확인

**4-3. Terrain 변화:**
- 실내 평지 → 실외 매끈한 보도블록 → 실외 일반 보도블록
